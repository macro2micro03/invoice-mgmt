# 반입송장 → 자재검수요청서 자동 생성 — 설계 문서

## 배경 및 목표

건설 현장에서는 자재(예: 철근)가 반입될 때마다 여러 장의 반입송장(택배사/제강사가 발행하는 "송장별 총괄 내역서")을 받는다. 현장 담당자는 이 송장들을 규격별로 합산해서, 감리단에 제출하는 정식 서식인 "자재검수요청서/검수결과통보"(갑지)를 손으로 작성해왔다. 이 문서는 지금까지 이 프로젝트에서 만든 "촬영→OCR→DB저장→검색" 앱과는 **완전히 별개의 새 기능**으로, 반입송장 PDF를 업로드하면 규격별 합산과 서식 작성을 자동화한다.

- **입력**: 여러 건의 반입송장이 합쳐진 PDF 1개 (각 송장은 "송장별 총괄 내역서"라는 제목의 갑지 + 상세 내역 페이지들로 구성되며, 상세 내역 페이지는 사용하지 않는다)
- **출력**: "자재검수요청서/검수결과통보"와 동일한 표 레이아웃의 워드(.docx) 파일
- **범위**: 기존 앱(백엔드 `backend/app/`, 프론트엔드 `frontend/src/`)에 새 라우트/화면을 추가하는 형태로 구현하며, 기존 촬영/저장/검색 기능은 건드리지 않는다.

## 실제 문서 구조 (검증됨)

첨부된 실제 파일(`302. 철근-65.pdf`, 21페이지)로 검증한 구조:

- 1페이지: 자재검수요청서/검수결과통보 (사람이 최종 확인하는 완성본 — 이번 기능이 만들어내는 결과물과 같은 서식)
- 2~7페이지: 체크리스트 등 참고 서류 (이번 기능에서 사용하지 않음)
- 8, 13, 18페이지: 각 반입송장의 갑지("송장별 총괄 내역서") — **이번 기능의 데이터 소스**
- 8/13/18페이지 각각 뒤에 딸린 상세 내역 페이지("제품(출고,인수)증") — 사용하지 않음

세 갑지의 규격별 발송중량(kg)을 합산한 결과가 정확히 1페이지의 규격별 수량(Ton)과 일치함을 확인했다:
- SHD10: 675 + 2,931 = 3,606kg = 3.606 Ton
- SHD13: 21,110kg = 21.110 Ton
- UHD16: 122kg = 0.122 Ton
- UHD19: 1,980kg = 1.98 Ton
- UHD25: 21,573 + 20,511 = 42,084kg = 42.084 Ton
- 총합: 68.902 Ton

## Upstage 응답 구조 (검증됨)

"송장별 총괄 내역서" 페이지는 Upstage document-parse에서 `category: "table"`인 두 개의 HTML 표로 인식된다:
1. 헤더 정보 표: 송장번호/현장명/인수장소/도착일/차량번호/특이사항/공사부위 — 단, 라벨 글자가 셀마다 쪼개져 있음(예: "송" | "장 번 호 :" | "20260331-023 (97 회차)")
2. 규격별 내역 표: `<thead>직경|단위중량(kg/m)|발송중량(kg)|할증중량(kg)|비고</thead>` + 규격별 행 + "총 합" 행
3. 반입업체명은 라벨 없이 큰 제목(`heading1`)으로 페이지 하단에 등장 (예: "동 경 강 업 ( 주 )")

## 아키텍처

```
[프론트: 새 화면 "보고서 생성"]
  - PDF 업로드
  - 1회성 입력: 공사명, 공종명(체크박스), 자재종류(품명), 발신자, 수신자
      |
      v  POST /reports/material-inspection (multipart)
[백엔드: 신규 모듈 app/report.py + app/routers/reports.py]
  1. PDF를 Upstage document-parse로 전달
  2. heading1 텍스트가 "송장별 총괄 내역서"인 페이지만 선별 (제목 매칭 기반 자동 감지)
  3. 각 갑지에서 규격별 표와 반입업체명(heading1 중 제목이 아닌 것)을 추출
  4. 규격(직경)별로 발송중량(kg)을 합산 → 1000으로 나눠 Ton 변환, 소수 3자리 반올림
  5. 거래처 = "반입업체명/비고" (예: "동경강업(주)/동국제강")
  6. 문서번호 회차를 DB에서 조회해 +1 증가, 저장
  7. python-docx로 템플릿을 채워 .docx 생성
      |
      v  응답: .docx 파일 다운로드
```

## 데이터 흐름 상세

**1. 갑지 탐지**: Upstage 응답의 `elements`에서 `category == "heading1"`이고 텍스트가 "송장별 총괄 내역서"인 페이지 번호를 모두 찾는다. 하나도 없으면 `400` 에러와 함께 "송장별 총괄 내역서 페이지를 찾을 수 없습니다" 메시지를 반환한다 (자동화 실패를 침묵 처리하지 않음).

**2. 갑지별 데이터 추출** (탐지된 각 페이지에 대해):
- 같은 페이지의 `category == "table"` 요소 중, `<thead>`에 "직경"이 포함된 표를 규격별 내역 표로 식별
- 표의 각 `<tr>`(단, "총 합" 행 제외)에서 직경(규격), 발송중량(kg)을 추출 — 쉼표(,) 제거 후 숫자로 변환
- 같은 페이지의 `heading1` 텍스트 중 "송장별 총괄 내역서"가 아니고 "송장중량"으로 시작하지 않는 것을 반입업체명으로 식별 (여러 갑지에 걸쳐 다르면 마지막으로 발견된 값을 사용)
- 표의 "비고" 컬럼 값(제조회사명, 예: "동국제강") 중 첫 번째 비어있지 않은 값을 사용

**3. 합산**: 모든 갑지에서 추출한 (규격, 발송중량) 쌍을 규격별로 그룹화해 발송중량을 합산, 1000으로 나눠 Ton으로 변환.

**4. 문서번호**: `backend/app/models.py`에 새 테이블 `ReportSequence`(단일 카운터 행)를 추가. 요청마다 마지막 값을 읽어 +1 한 뒤 저장하고, "건축(자검)-{자재종류}-{N}호" 형식으로 사용.

**5. 워드 생성**: `python-docx`로 1페이지와 동일한 표 레이아웃(공사명/공종명/승인구분/문서번호/접수일자/발신자/검수일자/수신자/검수위치, 자재 내역 표, 계, 검수요청일/현장대리인, 통보일자/총괄관리원, 미승인사유/처리방안, 붙임)을 채운 문서를 생성한다.
   - 자동 채움: 공사명/공종명/자재종류(사용자 입력), 문서번호(자동 증가), 접수일자/검수일자(오늘 날짜), 발신자/수신자(사용자 입력), 검수위치("현장 내" 고정), 자재 내역 표(규격/단위/수량/거래처), 검수결과 기본값 "적합"
   - 비워둠(사람이 직접 기입/체크): 승인구분, 미승인사유, 처리방안, 서명란

## 에러 처리

- 갑지를 하나도 못 찾으면 400 에러 + 명확한 메시지
- 규격별 표를 못 찾은 갑지는 건너뛰고, 어떤 페이지를 건너뛰었는지 응답에 경고로 포함
- Upstage 호출 자체가 실패하면 500 에러로 명확히 실패를 알림 (기존 앱의 "OCR 실패는 절대 막지 않는다" 원칙은 이 기능에는 적용하지 않음 — 이 기능은애초에 결과물이 정확해야 의미가 있으므로, 실패를 감추지 않고 사용자에게 알려 재시도를 유도한다)

## 테스트 전략

- 실제 파일(`302. 철근-65.pdf`)은 실명/전화번호/실제 현장명이 들어있어 저장소에 커밋하지 않는다. 대신 동일한 구조(갑지 3장 + 규격별 표 + 반입업체명 heading)를 가진 **합성 PDF**를 가짜 이름/전화번호로 만들어 `backend/tests/fixtures/`에 테스트 픽스처로 저장한다.
- 갑지 탐지, 규격별 합산, 문서번호 증가, docx 생성 각각에 대해 단위 테스트 (합성 PDF의 Upstage 응답을 흉내 낸 fixture dict로 네트워크 호출 없이 테스트)
- 실제 Upstage API로는 합성 PDF를 업로드해 엔드-투-엔드로 한 번 검증 (합산 결과가 알고 있는 합계와 일치하는지)

## 범위 밖 (이번 기능에 포함하지 않음)

- 승인/서명 절차 자동화 (사람이 출력 후 직접 처리)
- 반입업체명 인식 방식의 일반화 (다른 회사 서식 대응은 필요 시 추후 확장)
- 상세 내역 페이지("제품 출고인수증")의 개별 항목 활용
