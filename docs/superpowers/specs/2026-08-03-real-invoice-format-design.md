# 실제 철근 납품 확인서 양식 인식 — 설계 문서

## 배경

`backend/app/report_parser.py`의 다중 자재 갑지 인식 로직(`find_cover_pages`, `extract_material_rows`, `find_vendor_heading`, `find_delivery_date`, `find_vehicle_no`, `find_invoice_no`)은 "송장별 총괄 내역서"라는 제목과 "직경"/"발송중량(kg)" 컬럼을 가진 가상의 양식을 기준으로 작성되어 있었다. 실제 현장에서 사진으로 촬영하는 송장은 이 가정과 전혀 다른 "**철근 납품 확인서**" 양식(컬럼: 철근경/가공중량,Ton/할증(%)/로스감안중량,Ton/커플러/비고)이며, 현재 코드는 이 실제 문서를 인식하지 못해 대부분의 필드가 빈 채로 남는다. 현장은 이 양식 하나만 사용하므로, 기존 가상 양식 로직을 이 실제 양식 기준으로 전면 교체한다.

## 범위

**포함:**
- "철근 납품 확인서" 양식의 제목·표·라벨 인식으로 `report_parser.py` 전면 교체
- 표에서 규격(철근경)과 중량(로스감안중량,Ton — 이미 톤 단위, 변환 없이 사용) 추출
- 문서 전체 텍스트에서 납품일/송장번호/차량번호/공장명(거래처) 라벨 값 추출
- `/ocr`(다중 레코드 촬영)과 `/reports`(파일 업로드 보고서 생성) 두 경로 모두 자동 반영(둘 다 `report_parser`를 그대로 호출하므로 별도 라우터 수정 불필요)
- 실제 문서 내용을 반영한 회귀 테스트

**범위 밖:**
- 공사명/공정명/납품차수/착지주소 등 자재 저장에 불필요한 필드 캡처
- 이 양식 외의 다른 거래처별 양식 지원(현재는 이 양식 하나만 실사용)

## 필드 매칭 규칙

| 필드 | 문서 위치 | 비고 |
|---|---|---|
| 제목 | "철근 납품 확인서" | 글자 사이 공백 무시하고 비교(제목이 장식적으로 자간이 벌어진 경우 대응) |
| spec | 표의 "철근경" 열 | 예: SHD10, SHD13, UHD16, UHD22 |
| weight | 표의 "로스감안중량,Ton" 열 | 이미 톤 단위 — kg→ton 변환 하지 않음(기존 로직은 kg 가정 후 /1000 했었는데, 이 양식은 처음부터 Ton이라 그대로 사용) |
| 합계 행 제외 | "계"/"총합"/"총계"/"합계" | 표 첫 칸이 이 라벨 중 하나면 스킵 |
| vendor(거래처 표시) | "공장명:" 라벨 값 = 반입업체명, "비고" 열 값 = 제조회사명 | 최종 표시는 `반입업체명/제조회사명` (예: `(주)대건건철/동국제강,현대제철`) |
| delivery_date | "납품일:" 라벨 뒤 날짜(YYYY-MM-DD) | |
| invoice_no | "송장번호:" 라벨 뒤 숫자-대시-숫자 | 자릿수는 가변("숫자+"-"+숫자+" 패턴, 자릿수 고정하지 않음) |
| vehicle_no | "차량번호:" 라벨 뒤 값 | 이번 실제 샘플은 비어있음 — 빈 값이면 빈 문자열 반환(기존과 동일하게 필수 아님) |

## 아키텍처

### 라벨 값 추출: 표 안쪽이 아니라 문서 전체 텍스트 기준으로 전환

기존 `find_delivery_date`/`find_vehicle_no`/`find_invoice_no`는 표(`category == "table"`) 안의 행만 뒤졌는데, 실제 문서에서 납품일/송장번호는 표가 아니라 본문 단락(파라그래프) 텍스트에 있다. Upstage의 category 분류가 페이지마다 비결정적이라는 기존 주석의 경고와도 맞물려, 표/단락 구분에 의존하지 않고 **문서 전체를 하나의 텍스트로 펼친 뒤(`ocr.extract_text` 재사용) 라벨을 찾는 방식**으로 바꾼다.

표 셀은 셀 사이 구분자 없이 한 줄로 뭉쳐 나오는 경우가 있으므로(오늘 택 대조 기능에서 겪은 것과 같은 문제), 라벨 값 추출에는 "다음에 나오는 알려진 라벨 직전까지만 값으로 잡는" 비탐욕적(non-greedy) 정규식을 사용한다(택 OCR 파서 수정 때와 동일한 기법 재사용).

### 표 파싱: 컬럼명 기반, 위치 무관

기존 `extract_material_rows`처럼 헤더 셀 텍스트로 컬럼 인덱스를 찾는 방식은 그대로 유지하되, 찾는 컬럼명을 "직경"→"철근경", "발송중량"→"로스감안중량"으로 교체한다. 컬럼 순서가 바뀌어도 헤더 텍스트로 찾기 때문에 안전하다.

### 제목/거래처 인식

- `find_cover_pages`: 제목 비교 시 공백을 제거하고 비교(`철근납품확인서`로 정규화 후 비교)
- `find_vendor_heading`: 기존의 "heading1 텍스트 중 회사명처럼 보이는 것" 추측 방식을 버리고, "공장명:" 라벨 뒤 값을 직접 추출하는 방식으로 교체(더 명확하고 오탐 위험이 없음)

## 함수 시그니처 변경

`find_cover_pages`, `build_capture_records`, `build_report_data`의 **반환 형태는 그대로 유지**한다(호출부인 `routers/ocr.py`, `routers/reports.py`는 수정 불필요). 내부 구현만 교체한다.

`find_delivery_date(raw_response, page)`, `find_vehicle_no(raw_response, page)`, `find_invoice_no(raw_response, page)`, `find_vendor_heading(raw_response, page)`는 표 대신 `ocr.extract_text(raw_response)`로 얻은 문서 전체 텍스트를 대상으로 라벨을 찾도록 내부 구현을 바꾼다(시그니처는 유지 — `page` 파라미터는 현재 사실상 사용하지 않게 되지만, `build_capture_records`/`build_report_data`가 페이지별로 호출하는 기존 구조를 유지하기 위해 그대로 둔다).

## 테스트 전략

실제로 보내주신 문서 내용을 반영해 Upstage 응답 형태의 fixture를 재구성한다:
- 제목 요소: "철근 납품 확인서" (공백이 들어간 버전도 별도 테스트로 검증)
- 표 요소: 철근경/가공중량,Ton/할증(%)/로스감안중량,Ton/커플러/비고 헤더 + SHD10/SHD13/UHD16/UHD22 4행 + "계" 합계행
- 본문 텍스트: 공사명/공정명/납품차수/납품일/송장번호/착지주소 등을 포함한 문단

검증 항목:
- 4개 레코드가 정확한 spec/weight(로스감안중량 값 그대로, 변환 없음)로 추출되는지
- "계" 합계 행이 결과에 포함되지 않는지
- vendor가 `공장명/비고` 형태로 합쳐지는지
- delivery_date가 "2026-07-30", invoice_no가 "1178-001"로 추출되는지(자릿수가 다른 송장번호 케이스도 추가)
- 표 셀이 줄바꿈 없이 한 줄로 뭉친 경우에도 라벨 값이 다음 라벨과 섞이지 않는지(비탐욕적 정규식 회귀 테스트)
- 기존 `test_report_parser.py`의 가상 양식 기준 테스트는 이번 교체로 더 이상 유효하지 않으므로 삭제하고 새 양식 기준 테스트로 전면 교체

## 자체 점검

- 이 양식 하나만 실사용된다는 전제가 명시되어 범위가 명확함 — 확인됨
- 로스감안중량이 이미 톤 단위라 변환하지 않는다는 점이 명시됨(기존 kg→ton 변환 로직과의 차이가 혼동되지 않도록) — 확인됨
- 함수 시그니처를 유지해 호출부(`routers/ocr.py`, `routers/reports.py`) 수정이 불필요함이 명시됨 — 확인됨
- 표 셀 뭉침 문제에 대한 대응(비탐욕적 정규식)이 오늘 택 OCR 수정과 일관된 방식임이 명시됨 — 확인됨
